# 金融实时大数据分析平台 — 答辩文档

## 一、项目简介

基于 Docker 12 节点集群构建的金融实时行情分析平台，覆盖黄金、原油、白银、铜、天然气 5 个期货品种，25 万条 tick 级行情数据。实现从数据采集到可视化大屏的全链路自动化处理。

**技术栈：** Python + Kafka + Spark Streaming + Logstash + HDFS + Hive + Elasticsearch + FastAPI + ECharts + sklearn + DeepSeek

---

## 二、核心数据流转流程

### 整体链路

```
CSV(5文件25万条) → Producer(5条/秒) → Kafka(5个Topic) 
                                          │
                    ┌─────────────────────┼─────────────────────┐
                    ▼                                           ▼
            Spark Streaming                                Logstash
            (10秒微批)                                   (数据清洗)
                    │                                           │
                    ▼                                           ▼
                 HDFS                                      Elasticsearch
          /user/finance/raw/                          finance_realtime_metrics
          /user/finance/agg/1min/                            │
                    │                                           │
                    ▼                                           ▼
            Hive 四层数仓                                    FastAPI
         (ODS→DWD→DWS→ADS)                              (15个REST端点)
                    │                                           │
                    └──────────────┬────────────────────────────┘
                                   ▼
                              ECharts 大屏
                           (5秒轮询, 14个区域)
```

### 分步讲解

#### 第 1 步：数据生产（CSV → Kafka）

**做什么：** 5 个 CSV 文件，每个 5 万条 tick 数据，Python Producer 逐行读取，JSON 序列化后按 5 条/秒发送到 Kafka。

**用到的组件：** Python + kafka-python 库

**关键配置：** Kafka acks=all（保证不丢数据）、gzip 压缩（减小网络传输）、5 个 Topic 各 3 分区

**对应大屏：** 数据资产统计面板 — 显示 CSV 行数和 HDFS 文件数

---

#### 第 2 步：消息缓冲（Kafka）

**做什么：** 数据进入 Kafka 暂存，解耦生产者和消费者。生产者只管发，消费者按自己的节奏取，互不影响。

**用到的组件：** Apache Kafka + ZooKeeper

**关键设计：** 5 个 Topic（gold_tick、oil_tick、silver_tick、copper_tick、gas_tick），每个 3 分区，支持多消费者组独立消费

**对应大屏：** 无直接展示（Kafka 属于中间层，其作用体现在整个系统的解耦能力上）

---

#### 第 3 步：双消费者分流（核心设计）

**为什么分两路：** Spark 擅长写 HDFS 做离线计算，Logstash 擅长写 ES 做实时管道，各司其职。一条挂了另一条不受影响。

##### 上路：Spark Streaming → HDFS

**做什么：** 每 10 秒触发一批微批处理，从 Kafka 消费数据，做两件事：
1. 原始 tick JSON → 按品种和日期分区写入 HDFS（`/user/finance/raw/gold/dt=2026-07-11/`）
2. 1 分钟窗口 OHLC 聚合 → 写入 HDFS（`/user/finance/agg/1min/gold/dt=2026-07-11/`）

**用到的组件：** Apache Spark Structured Streaming + HDFS（NameNode + DataNode）

**对应大屏：** Spark K线图（OHLC candlestick）+ Spark 作业状态卡片

##### 下路：Logstash → Elasticsearch

**做什么：** 同时消费 Kafka，做数据清洗（date 解析、类型转换、衍生字段计算），批量写入 ES。

**用到的组件：** Logstash + Elasticsearch

**对应大屏：** 行情卡片、趋势图、成交量图、风险雷达、风险面板 — 所有实时数据都走这条链路

---

#### 第 4 步：数据存储与建模

**HDFS：** 数据湖，原始 tick JSON + OHLC 聚合 JSON 永久存储，三副本保证可靠性。

**Hive 四层数仓：**
| 层 | 数据库 | 存储 | 内容 |
|----|--------|------|------|
| ODS | ods_finance | HDFS 外部表 JSON | 原始 tick，与 Spark 写入路径对齐 |
| DWD | dwd_finance | ORC + Snappy | 清洗后明细，新增 mid_price/spread_pct |
| DWS | dws_finance | ORC + Snappy | 1min/5min OHLC 窗口聚合 |
| ADS | ads_finance | ORC + Snappy | 大屏直读指标（latest_snapshot/dashboard_metrics）|

**Elasticsearch：** 实时搜索引擎，finance_realtime_metrics 索引存储每条 tick，refresh_interval=5s 近实时可见。

**对应大屏：** 相关性矩阵标注为"Hive ODS"（数据来自 Hive 外部表映射的 HDFS 数据）

---

#### 第 5 步：数据服务（FastAPI）

**做什么：** 统一数据服务层，15 个 REST 端点聚合所有数据源的查询。

| 端点 | 数据源 | 大屏对应区域 |
|------|--------|-------------|
| /api/realtime/latest | ES | 5 张行情卡片 |
| /api/realtime/trend | ES | 价格趋势图 |
| /api/realtime/volume | ES | 成交量柱状图 |
| /api/realtime/risk | ES + Python 计算最大回撤 | 风险雷达图 + 风险面板 |
| /api/spark/ohlc | HDFS (Spark 聚合结果) | K线图 |
| /api/spark/status | Spark Master API :8080 | Spark 状态卡片 |
| /api/analysis/correlation | Hive ODS / CSV | 相关性矩阵 |
| /api/ml/predict | ES + sklearn 模型 | ML 预测面板 |
| /api/chat | DeepSeek API | AI 对话 |

**用到的组件：** FastAPI + uvicorn

---

#### 第 6 步：可视化（ECharts 大屏）

**做什么：** 纯 HTML+ECharts 大屏，每 5 秒通过 Fetch API 轮询 FastAPI 端点，拿到 JSON 后渲染图表。

**14 个功能区域：** 顶栏状态 → 5 张行情卡片 → 趋势图 + 成交量 → Spark K线 + 状态 → 风险雷达 + 面板 → 数据资产 + 预览 + 搜索 → 相关性矩阵 + 配对 → ML 预测 → AI 对话

**用到的组件：** ECharts 5.4.3 + 原生 JavaScript

---

## 三、机器学习价格方向预测

### 3.1 问题定义

**目标：** 根据当前和历史 tick 数据，预测下一个 tick 的价格方向是涨（UP）还是跌（DOWN）。

**本质：** 二分类问题（1 = UP, 0 = DOWN）

---

### 3.2 特征工程（15 个特征）

从 CSV 原始字段中提取技术指标作为模型输入：

| 序号 | 特征 | 含义 | 计算方式 |
|------|------|------|----------|
| 1 | price_lag1 | 上一条价格 | 前移 1 位 |
| 2 | price_lag2 | 上两条价格 | 前移 2 位 |
| 3 | price_chg1 | 价格变化率 | (当前-上条)/上条 × 100 |
| 4 | sma_cross_5_10 | 短期均线交叉 | (SMA5 - SMA10)/价格 × 100 |
| 5 | sma_cross_10_20 | 长期均线交叉 | (SMA10 - SMA20)/价格 × 100 |
| 6 | rsi_14 | 相对强弱指标 | RSI = 100 - 100/(1 + RS) |
| 7 | momentum_5 | 5 周期动量 | (当前-5条前)/5条前 × 100 |
| 8 | momentum_10 | 10 周期动量 | (当前-10条前)/10条前 × 100 |
| 9 | bb_position | 布林带位置 | (价格-中轨)/(2×标准差) |
| 10 | vol_ratio | 成交量比率 | 当前量/5 期均量 |
| 11 | vol_change | 成交量变化 | (当前量-5条前量)/5条前量 × 100 |
| 12 | spread_pct | 价差比例 | 价差/价格 × 100 |
| 13 | high_low_pct | 日内振幅比 | (最高-最低)/价格 × 100 |
| 14 | bid_ask_mid | 买卖偏离 | (买价+卖价)/2 - 价格 |
| 15 | volatility | 波动率放大 | volatility × 10000 |

---

### 3.3 模型训练

**算法：** VotingClassifier 集成投票（GradientBoostingClassifier + RandomForestClassifier）

- GradientBoosting：100 棵树，学习率 0.1，逐棵纠错，拟合残差
- RandomForest：100 棵树，Bagging 随机采样，投票防止过拟合
- 投票方式：soft voting — 两个模型各输出 UP/DOWN 概率，取加权平均

**数据量：** 25 万条 tick 数据，去掉滚动窗口 NaN 后有效样本约 12.5 万条

**训练/测试：** 80% 训练 / 20% 测试，3 折交叉验证

**结果：**
- 测试集准确率：51.82%
- 基准准确率（瞎猜 UP）：49.59%
- 交叉验证：51.57% ± 0.15%

**为什么准确率不高？** tick 级别的短期价格走势接近随机游走，方向预测本身极其困难。在量化交易领域，能稳定比随机高 1-3% 已有实际价值。

---

### 3.4 实时推理部署

**训练阶段（Windows 本地）：**
```
5个CSV → 特征提取(15个) → VotingClassifier 训练 → joblib 保存模型文件
```

**推理阶段（每 5 秒，Ubuntu 服务器）：**
```
ES 取最新 60 条 tick → 计算 15 个特征 → 加载 joblib 模型 → predict_proba → 输出 UP/DOWN + 概率
```

**关键点：**
- 推理输入从 ES 实时获取（不是静态 CSV），随数据流实时变化
- 每 5 秒计算一次，新数据进来后特征重新计算，预测结果跟着跳动
- FastAPI 启动时加载模型到内存，后续推理无需重复加载
- ES 不可用时自动回退到 CSV 静态数据

**对应大屏：** ML 预测面板 — 5 个品种各显示预测方向（▲UP/▼DOWN）、涨跌概率进度条、置信度和模型准确率

## 四、为什么要两条链路分开？

| 对比 | Spark → HDFS | Logstash → ES |
|------|-------------|---------------|
| 写入目标 | HDFS 数据湖 | ES 搜索引擎 |
| 查询速度 | 秒级（Hive SQL） | 毫秒级（ES REST） |
| 用途 | 离线分析、永久存储 | 大屏实时展示 |
| 数据类型 | 原始 JSON + OHLC 聚合 | 清洗后的明细 |
| 依赖关系 | 独立，不依赖 ES | 独立，不依赖 HDFS |

如果只用一个：只用 Spark 写 HDFS，大屏查 Hive 太慢（秒到十秒），无法 5 秒刷新；只用 Logstash 写 ES，数据在 Kafka 过期后就丢了，无法做历史分析。两条链路互补，才是完整的大数据架构。

## 五、答辩要点速记

```
数据流一句话：
CSV → Producer → Kafka → (Spark→HDFS/Hive) + (Logstash→ES) → FastAPI → ECharts

大屏从上到下指哪讲哪：
顶栏 → 行情卡 → 趋势/成交量 → Spark K线 → 风险 → 相关性 → ML → AI

每块三板斧：
1. 展示什么    2. 数据从哪来    3. 什么组件、起什么作用

核心组件职责：
Kafka: 消息缓冲解耦    Spark: 流计算+数据持久化
Logstash: 数据管道清洗  HDFS: 数据湖永久存储
Hive: 数仓建模        ES: 毫秒级实时查询
FastAPI: 统一服务层    ECharts: 可视化
sklearn: ML预测       DeepSeek: AI对话
```
